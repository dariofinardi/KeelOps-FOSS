# The database and the two editions

KeelOps has **one database schema** for the community and the commercial edition: switching edition is a configuration change (`KEELOPS_EDITION`), never a migration, in both directions. The commercial modules keep their data in the tables below and in a few columns of core tables; the community leaves those tables empty, those columns at their default, and ignores the values listed under *Values*. This page is generated by `scripts/genera-schema-edizioni.mjs` from `edizioni/schema-edizioni.txt` and `edizioni/dto-edizioni.txt`; a test keeps it in step with `schema.prisma`.

## The core keeps the commercial rows consistent

A community started on a database that was commercial finds rows in the commercial tables. Two of them point at `User` with a foreign key that forbids deleting the user (`DealAnalysis.requestedById`, `InjectClient.serviceUserId`), so the **core** — in both editions — moves or checks those rows when a user is deleted or merged (`modules/users/deletion.ts`, `modules/users/migration.ts`): without that, the community would fail with a bare database error on a user it cannot see the reason for. The other commercial tables cascade or set null on their own. This is a deliberate seam, decided on 10/10/2026: the schema stays one, and the core knows the few commercial tables it must not break.

## Values

Core columns whose **values** can belong to the commercial edition. A community started on a commercial database finds rows with these values and does not serve them: a portal customer cannot sign in, a request stays out of every list, a notification of these types is not shown.

|---|---|---|
| `Task.kind` | `TICKET` | ticket — a request is a task of this kind |
